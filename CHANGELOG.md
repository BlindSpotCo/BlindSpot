# Data & scoring changelog

Item 7 of the trust-framework checklist: "Version your scoring model... publish a simple changelog... monitor impact." This file starts that practice - it is reconstructed from git history up through this entry, and should be updated by hand (or by whatever patches `data/aslivastu/*.json`) from here on, every time a data source, weight, or scoring method changes for any dimension in any city.

Version numbers are for this dataset/methodology, not the app (`package.json`'s `version` is separate).

## v1.11 - 2026-09-23

- Fixed a grade-label bug affecting 106 of 343 pincodes (31% of the entire dataset): 59 Delhi NCR and 47 Bangalore records were showing a letter grade one or two notches harsher than their own composite score warrants (`scripts/patch_grade_labels.py`). Root cause: five patch scripts (`patch_delhi_power.py`, `patch_delhi_aqi.py`, `patch_bangalore_power.py`, `patch_bangalore_aqi.py`, `patch_bangalore_water.py`) each defined their own inline `grade_for()` using a coarser five-band scale (A/B/C/D/F, no B+/C+) instead of the canonical six-band scale every city's build script actually uses (A/B+/B/C+/C/D). Every time one of those scripts ran, it silently overwrote the affected records' `grade` field on that wrong scale, even though the underlying `nqi_composite` was always computed correctly. This was found while investigating task 4 of the pre-monetization audit punch list (pincode 123106's incomplete grade) and turned out to be a much larger, separate bug. Mumbai, Hyderabad, Chandigarh and Chennai were never touched by these scripts and are unaffected. Only the `grade` label was changed; no composite, score or weight was touched.
- Closed out pincode 123106 (Dharuhera, Rewari district, tagged Delhi NCR), the one record in the dataset scored on only 2 of 8 dimensions while still carrying a full composite and grade (Tier 3 of the audit, task 4 of the punch list). It already had real DHBVN power data in `master_by_pin.json` (from `patch_delhi_power.py`), computed but never written into its `nqi_scores.json` score dict. Added it (`scripts/patch_123106_power.py`), taking this pincode from 2/8 to 3/8 scored dimensions using the exact same DISCOM_POWER_SCORE methodology already applied to every other Delhi NCR pincode. Its remaining 5 dimensions (crime, water, roads, sewerage, and infrastructure beyond metro) still have no source data for this small industrial Haryana pincode and are left honestly absent, not fabricated.

## v1.10 - 2026-09-23

- Closed the biggest open item from the pre-monetization audit: Mumbai's and Hyderabad's `metro_stations_nearby` field was mostly unverified (48% and 80% of their pins respectively carried an unsourced 0, still the old zone/jitter-derived value). Built a real, named, sourced metro station registry for both cities (`MUMBAI_STATIONS`, 66 stations across Lines 1/2A/3/7; `HYDERABAD_STATIONS`, 53 stations across Red/Blue/Green) in `scripts/metro_stations.py`, the same file that already carried Delhi NCR and Bangalore's registries from v1.4, then re-ran the same centroid-radius join (1.5km) against all 96 Mumbai and 41 Hyderabad pincodes.
- No bulk coordinate dataset exists for either city's metro (checked again, same as v1.4's finding), so this was built station by station, mostly from Wikipedia infobox coordinates, cross-checked for internal consistency before use. That per-station checking caught 4 real Wikipedia data errors that a bulk import would have silently inherited: Mumbai's Asalpha station infobox is a near-duplicate of Jagruti Nagar's coordinate; Hyderabad's Dr B R Ambedkar Balanagar and Habsiguda infoboxes are geographically implausible or duplicate another station; Hyderabad's Parade Ground infobox is a byte-for-byte copy of Punjagutta's, a station 5.9km away. Each was corrected using an independent source before use, not propagated. 3 Hyderabad stations (ESI Hospital, Nampally, Gandhi Bhavan) have no reliable coordinate anywhere checked and are left out of the registry entirely rather than guessed, same discipline as everywhere else in this dataset. Monorail stations and lines still under construction (Mumbai Line 6, Hyderabad Phase 2) are excluded, this registry is currently-operational metro only.
- Result: 77 of 137 Mumbai+Hyderabad pins changed value (both directions: several pins carried an unsourced "1" in areas no currently-operational line actually reaches, alongside the expected undercounts), and 59 more pins had their existing value confirmed correct and given a real citation for the first time. Full per-pin detail is in the commit diff's `_provenance` entries, not repeated here.
- Worth a human sanity check, not silently resolved: a handful of pins, Hyderabad's Miyapur (2.24km from its own namesake terminal station) and Mumbai's Bandra West (2.38km from Bandra Colony) among them, have a pincode centroid sitting further from their namesake or nearest station than the standard 1.5km radius. Kept consistent with the same radius standard applied to every other pin in this dataset (including the Juhu/Gachibowli/Kondapur cases closed out in v1.9) rather than special-cased, but these specific "named after a station that's technically just outside the radius" cases are worth a second look, the same reasoning that got 201309 (Noida Sector 62) a manual override in v1.8 could arguably apply here too.

## v1.9 - 2026-09-23

- Closed out the 3 "needs a closer look" pincodes flagged in v1.8 (400049 Juhu, 500032 Gachibowli/Financial District, 500084 Kondapur/Kothaguda). Recomputed each using the pincode's own official centroid from `lib/aslivastu/areaCoords.js` (the same coordinate BlindSpot's own automated join uses), not a generic "nearest to the neighbourhood name" web search result, which is what made these look borderline in the first place. Juhu's centroid is 2.71km from Andheri metro (a closer 1.23km figure from a general search was measuring from a different point within the broader Juhu area, not this pincode's own centroid). Gachibowli/Financial District is 3.02km from Raidurg, the nearest real station. Kondapur/Kothaguda is 2.65km from Raidurg (Madhapur is even further from both). All three are correctly 0 using the same 1.5km radius standard applied everywhere else in this dataset. No data changed.
- Worth a note for anyone reading `scripts/build_hyderabad.py`'s own Cyberabad comment: it says "HITEC City/Madhapur/Kondapur ARE metro-served," but that's true for the HITEC City/Madhapur pincode (500081, which does sit next to Raidurg and Madhapur stations), not for the separate Kondapur/Kothaguda pincode (500084) checked here. Same neighbourhood name, two different pincodes, only one of them is actually near a station.

- Ran a full pre-monetization audit across all 4 validators, every city, every pincode, plus a codebase search for the schools_list bug class and a real-source spot check on the validator's cross-field-contradiction flags (commercial zone + weak infra + 0 metro, the Connaught Place bug pattern). Full findings in `pre-monetization-data-audit-2026-09-22.md` (not committed to this repo, kept as a working document).
- Fixed 4 confirmed-wrong `metro_stations_nearby` values found by that audit: 201309 (Noida Sector 62/62A, Delhi NCR), 400052 (Khar West, Mumbai), 500082 (Somajiguda, Hyderabad), 500073 (Srinagar Colony, Hyderabad). ## v1.7 - 2026-09-22

- Fixed a real production bug found while reviewing a live Chennai report page: Hyderabad's and Chennai's `schools_list` was stored as an array of plain strings, while Delhi NCR's and Bangalore's was an array of objects (`{name, address, board, pass_pct, distance_km}`). `AVDetailedReadout.js` only ever knew the object shape, so on Hyderabad/Chennai `sc.name` came back blank and `sc.board` silently fell back to a hardcoded `'CBSE'` default, on all 217 of their named schools, regardless of the school's actual board. Reshaped both cities' `schools_list` to the same object schema. Board is populated only where a school's own registered name states it (`Kendriya Vidyalaya` -> CBSE, a literal `CBSE`/`ICSE` in the name, or `Matriculation` -> Tamil Nadu's Matriculation Board): 25 of 217 schools qualified. The other 192 are left `board: null`, shown in the UI as "Board not confirmed" rather than defaulting to CBSE, matching Hyderabad's own build-script docstring, which already said board wasn't reliably determined at the single-school level this pass. `address`/`pass_pct`/`distance_km` were never captured for either city's schools and stay `null`, not fabricated.
- Also fixed `scripts/build_chennai.py` and `scripts/build_hyderabad.py` (both got a shared `infer_school_board()` helper) so a future re-run of either generator produces the same object shape, instead of regressing back to plain strings.
- Separately noted, not fixed this pass: Delhi NCR's and Bangalore's existing `schools_list` boards are already 100% `'CBSE'` across all 796 entries, which is either a genuinely CBSE-only source or the same kind of unverified default this fix just removed elsewhere. Worth checking before trusting that field at face value.

## v1.5 - 2026-09-19

## v1.3 - 2026-09-13

- AQI/air score rebuilt on real CPCB/KSPCB station data with inverse-distance-weighted interpolation, replacing zone-baseline-plus-jitter, for Mumbai, Hyderabad, Chandigarh and Bangalore (`scripts/cpcb_stations.py`). Delhi NCR intentionally NOT included - the available real station readings skewed to a pollution-season sample (mean AQI ~333 vs. a commonly-cited annual ~150–220); applying it as-is would have dropped Delhi's composite scores by up to 21 points on a non-representative sample. Kept as researched, unapplied work pending a re-anchor against real annual figures.

## v1.0 - 2026-07-28

- Original baseline: Delhi NCR + Bangalore, 309 pincodes across the full dataset's eventual 5-city footprint, 8 scored dimensions (crime, infrastructure, air, power, schools, water, roads, sewerage). Large parts of this baseline were later found to be zone-modelled-plus-hash-jitter rather than measured (see `docs/data-integrity-architecture.md` section 1) - Bangalore's entire dataset was self-labelled `bengaluru_seed`. Every version above this one is, in part, a fix to something in this baseline.
