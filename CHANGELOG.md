Item 7 of the trust-framework checklist: "Version your scoring model... publish a simple changelog... monitor impact." This file starts that practice - it is reconstructed from git history up through this entry, and should be updated by hand (or by whatever patches `data/aslivastu/*.json`) from here on, every time a data source, weight, or scoring method changes for any dimension in any city.

Version numbers are for this dataset/methodology, not the app (`package.json`'s `version` is separate).

## v1.16 - 2026-09-24

- Fixed a crime score / crime tier contradiction across all 7 cities, reported by a user reviewing the live data: Bangalore 560066 (Whitefield) showed "Safety 75/100" right next to "safer than 18% of tracked areas, Very High crime tier" -- a genuinely decent absolute score labelled as one of the worst areas in the city. 176 of 381 scored pincodes showed the same >25-point score-vs-percentile gap.
- Root cause was structural, not a one-off: crime_percentile and crime_tier were both a within-city rank of a separately-modelled crime count, then displayed next to scores.crime, an absolute 0-100 measure. A same-city rank always stretches to fill 0-100 regardless of how tightly the real scores cluster, so a fine absolute score could still land at the bottom of its own city's narrow distribution. Confirmed even in Chandigarh, whose score and count correlate at r=-0.98: 11 of its 20 pincodes still showed the same gap, from the stretching effect alone. Mumbai/Hyderabad/Chennai/Ahmedabad/Bangalore's own crime patch additionally amplified this: their shared crimes_for() formula added an independent +/-40 jitter on top of the score-derived count, worth +/-8 points of pure noise at that formula's 5-crimes-per-point slope, further decorrelating the count's rank from the score.
- Fix: crime_percentile stays a same-city relative rank, but now ranks scores.crime directly instead of the noisy count, so it can no longer flip direction against the score. crime_tier is no longer percentile-based at all -- it is now an absolute threshold on scores.crime (Very Low >=80, Low >=70, Moderate >=60, High >=50, Very High else), the same grade_for() bands used platform-wide, matching how every other quality label here already works (reliability/road_condition/treatment are all direct thresholds of their own score, never a same-city rank). Verified zero score-vs-tier mismatches and zero percentile-vs-score monotonicity violations across all 381 scored pincodes after the fix.
- Also fixed the same absolute-tier logic at the source in build_mumbai.py, build_hyderabad.py, build_chennai.py, build_ahmedabad.py, build_chandigarh.py and patch_bangalore_crime.py, so a future re-run (adding a pincode, or an 8th city copied from one of these as a template) can't regress back into this bug.
- Separately, Bangalore-only: patch_bangalore_crime.py (v1.12) had updated total_cognizable_crimes in master_by_pin.json but never wrote the same field into nqi_scores.json, leaving nqi's own copy stale (Whitefield's two files disagreed: master 265, nqi 360). Synced nqi to master for all 66 Bangalore records. Re-checked every other field the two files share for the same desync pattern -- none found.
- Full validator suite + npm run build re-run clean: same pre-existing, already-documented findings only (zero-variance utility fields, Delhi/Bangalore coverage-gap pincodes), no new failures. Also re-verified grade-label consistency, schools_list shape, pincode collisions, weights_applied renormalization, and metro station registry duplicate-coordinates across the full current 382-pincode dataset -- all clean.

## v1.13 - 2026-09-23

- Fixed the validator's own vocabulary whitelist (`scripts/quality_metrics.py`'s `EXPECTED_VOCAB`), the last item on the pre-monetization audit punch list. It only allowed grades `A, B, C, D, F` and treatment values `Adequate, Partial, Inadequate` -- the dataset legitimately uses `B+`/`C+` (real outputs of the canonical grade_for() scale) and `Full` (a real treatment level, 28 records) as intentional values, not typos. Every one of the 343 records currently has a real city and a real, non-null `metro_stations_nearby`, so neither ever fires today -- but a future record missing either field would otherwise have silently shown an invented value instead of an honest gap. Now shows "not confirmed" for a missing metro count and drops the city name from the crime sentence instead of guessing one.

## v1.11 - 2026-09-23

- Fixed a grade-label bug affecting 106 of 343 pincodes (31% of the entire dataset): 59 Delhi NCR and 47 Bangalore records were showing a letter grade one or two notches harsher than their own composite score warrants (`scripts/patch_grade_labels.py`). Root cause: five patch scripts (`patch_delhi_power.py`, `patch_delhi_aqi.py`, `patch_bangalore_power.py`, `patch_bangalore_aqi.py`, `patch_bangalore_water.py`) each defined their own inline `grade_for()` using a coarser five-band scale (A/B/C/D/F, no B+/C+) instead of the canonical six-band scale every city's build script actually uses (A/B+/B/C+/C/D). Mumbai, Hyderabad, Chandigarh and Chennai were never touched by these scripts and are unaffected. Only the `grade` label was changed; no composite, score or weight was touched.
- Closed out pincode 123106 (Dharuhera, Rewari district, tagged Delhi NCR), the one record in the dataset scored on only 2 of 8 dimensions while still carrying a full composite and grade (Tier 3 of the audit, task 4 of the punch list). It already had real DHBVN power data in `master_by_pin.json` (from `patch_delhi_power.py`), computed but never written into its `nqi_scores.json` score dict. ## v1.7 - 2026-09-22

- Fixed a real production bug found while reviewing a live Chennai report page: Hyderabad's and Chennai's `schools_list` was stored as an array of plain strings, while Delhi NCR's and Bangalore's was an array of objects (`{name, address, board, pass_pct, distance_km}`). `AVDetailedReadout.js` only ever knew the object shape, so on Hyderabad/Chennai `sc.name` came back blank and `sc.board` silently fell back to a hardcoded `'CBSE'` default, on all 217 of their named schools, regardless of the school's actual board. - Also fixed `scripts/build_chennai.py` and `scripts/build_hyderabad.py` (both got a shared `infer_school_board()` helper) so a future re-run of either generator produces the same object shape, instead of regressing back to plain strings.
- Separately noted, not fixed this pass: Delhi NCR's and Bangalore's existing `schools_list` boards are already 100% `'CBSE'` across all 796 entries, which is either a genuinely CBSE-only source or the same kind of unverified default this fix just removed elsewhere.
